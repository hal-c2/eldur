Why we stopped rewriting our build system every two years

By Maya Chen · 12 October 2026 · 9 min read

Every few years our team felt the same itch: the build was slow, the configuration had grown brittle, and someone had found a newer tool that promised to fix everything. We rewrote it three times before we understood the real problem.

The first rewrite moved us from a set of hand-written scripts to a single orchestrator. It worked for a while. Then the scripts came back in the form of pre-build.sh hooks, one for each team, each with its own idea of what a clean checkout means.

The second rewrite replaced the orchestrator with a faster one. Builds dropped from eleven minutes to four, and everyone celebrated. Six months later, the cache was returning stale artifacts for about one change in fifty, and nobody could say which change.

The tool was never the problem. We kept changing the tool because it was easier than agreeing on what a build is supposed to guarantee.

The third time we started with a question instead of a tool: what must be true about an artifact before we are allowed to ship it? The answer was short. A build must be reproducible from its inputs, and every input must be declared.

Note. Declared inputs are not the same as fast builds. The speedup came from the cache finally being trustworthy, which let us stop disabling it on CI.

The steps we took

  1. Listed every file, environment variable and tool version that a build reads, and removed the ones nobody could justify.
  2. Hashed those inputs and used the hash as the only cache key, with no timestamps involved.
  3. Ran each build twice on separate machines and failed the pipeline if the outputs differed.
  4. Moved the per-team hooks into the repository as declared steps, so they show up in review like any other change.

None of these steps is novel. The discipline was in refusing to skip the first one when the tooling made it tempting to jump straight to the second.
